## Contract purpose

V1 is a fixed, server-owned observation capability. It is not general Hermes chat, not a generic run API, and not a natural-language authority evaluator.

The first action is intentionally one fixed read operation:

`observe.ai_country.health`

The action reads one server-configured, allowlisted health source using a fixed GET. The client cannot select the source, URL, method, headers, query, tool, provider, model, profile, session, memory operation, or command. The exact health source is an implementation/deployment constant and must be a bounded local/private read target; it is not accepted from the request.

No session, run, memory receipt, rollback reference, approval, or follow-up identifier is created or returned. The only permitted side effects are bounded service audit/journal entries and the target's ordinary operational access logging/metrics; no business-state, configuration, session, memory, approval, rollback, or target-write side effect is permitted. The audit format and retention are bounded below.

## Listener and routes

The observation service is a separate Hermes process/service and listener. It has its own bind address/port or protected Unix socket. It is not a profile prefix on the normal listener.

Registered HTTP routes:

- `GET /health` — unauthenticated liveness only: exact `200 {"status":"ok"}`; no inventory, configuration, target data, or credential-dependent details.
- `POST /v1/observation` — authenticated fixed observation action.

No other route is registered on this listener. In particular, there is no `/v1/runs`, `/v1/chat`, `/v1/responses`, `/api/sessions`, approval, stop, fork, delete, memory, MCP, tool, terminal, delegation, cron, provider, or arbitrary proxy route.

Allowed method:

- `POST` only on `/v1/observation`.
- Other methods return `405` without contacting the health target.
- Any other path returns `404` without contacting the health target.

Route normalization must reject the raw request-target unless it is exactly the origin-form octets `/v1/observation`. The listener must reject encoded slashes, dot segments, path traversal, fragments, query strings, absolute-form targets, duplicate or conflicting path headers, `X-HTTP-Method-Override`, `Forwarded`, `X-Forwarded-*`, and proxy override headers before framework normalization can turn them into an accepted route. The implementation must either use a parser/framework hook that exposes raw request-target and raw header multiplicity or prove these cases through the actual listening socket. The accepted route is exactly `/v1/observation`.

## Authentication

The service has a distinct observation credential, represented operationally as `HERMES_OBSERVATION_KEY`. It is not `API_SERVER_KEY`, any AI Country generic Hermes credential, or any mutation broker credential.

Authentication is checked before request-body parsing, action lookup, target access, or attacker-controlled audit content.

Accepted request authentication is exactly one `Authorization` header with scheme `Bearer` and the observation credential. Missing, malformed, duplicated, generic, expired, revoked, or wrong-profile credentials return `401` with the bounded error schema. The service never accepts a client-supplied alternate credential field, cookie, query token, forwarded identity, or fallback ambient credential.

The observation key is rejected by the normal Hermes listener. The generic Hermes key is rejected by the observation listener. Equality between the two configured values is a startup/configuration failure and the observation service must remain unavailable.

Credential values never appear in logs, errors, audit records, responses, process arguments, or ordinary environment dumps. Credential rotation replaces the observation credential without widening its capability. Revocation causes subsequent requests to fail at the service boundary.

## Request schema

Content type must be exactly one `Content-Type` header whose value is the case-insensitive media type `application/json` with no parameters, surrounding whitespace, or duplicate value. Maximum body size is 256 bytes, enforced before buffering/parsing.

The body must be one semantically exact UTF-8 JSON object with this member set and value:

```json
{"action_id":"observe.ai_country.health"}
```

Insignificant JSON whitespace is accepted; the server emits compact canonical JSON responses. Duplicate-key detection must operate on the original JSON token stream before object construction. No other member, byte-order marker, trailing non-whitespace byte, or second JSON value is accepted.

Rules:

- exactly one JSON object;
- exactly one key: `action_id`;
- exactly one string value with the exact action ID;
- duplicate keys are rejected, not last-write-wins;
- arrays, nested objects, null, numbers, unknown actions, extra fields, whitespace-only bodies, invalid UTF-8, invalid JSON, and oversized bodies are rejected;
- reject `profile`, `provider`, `model`, `tools`, `mcp`, `operation`, `url`, `method`, `headers`, `command`, `session`, `session_id`, `approval`, `memory`, `callback`, `redirect`, and any other field rather than ignoring it;
- no query parameters or fragments may carry authority.

A mutation-shaped natural-language string is not accepted as an action selector in V1. If AI Country has classified such text as observation, it remains untrusted context outside this fixed action schema and cannot change the operation.

## Success response schema

Successful observation returns exactly one bounded JSON object with no credential, URL, session, run, memory, rollback, tool, provider, model, or arbitrary target identifiers:

```json
{
  "action_id": "observe.ai_country.health",
  "observation_identity": "hermes-observer",
  "mutation_capability": "none",
  "provenance": "real_observation",
  "observed": {"status": "ok"},
  "limitations": []
}
```

The `observed` object is the fixed target's allowlisted bounded health projection. It is not a raw upstream response. Unknown target fields are discarded or cause a fail-closed error according to the implementation test contract. Response size is capped at 64 KiB.

The response never contains `run_id`, `session_id`, memory references, rollback references, approval references, links, callbacks, or server-returned identifiers that could cause a later request.

## Error response schema

All errors use a bounded shape and do not expose paths, configuration, target response bodies, credentials, stack traces, or attacker-controlled strings:

```json
{"error":{"code":"<fixed-code>","message":"<fixed-message>"}}
```

Required mappings:

- `400` `invalid_request` — malformed, duplicate, extra, unknown, or unsupported request;
- `401` `unauthorized` — missing, malformed, wrong, generic, revoked, or invalid observation credential;
- `404` `not_found` — any non-registered path;
- `405` `method_not_allowed` — any method other than POST on the observation route;
- `413` `request_too_large` — body exceeds 256 bytes;
- `429` `rate_limited` — bounded service rate limit, if configured;
- `502` `observation_unavailable` — fixed target failed, returned an invalid projection, or returned a redirect;
- `503` `observation_disabled` — service is not correctly configured or the observation credential/key separation check fails.

Error responses do not contact the health target unless the authenticated request has passed complete schema validation.

## Target transport

The service performs one fixed `GET` to a literal, deployment-pinned target address and path. V1 permits only an exact loopback literal (`127.0.0.1` or `::1`) plus one fixed port/path from the service unit; DNS names, URL schemes supplied by configuration, Unix-to-TCP fallback, proxy environment variables, and alternate address families are not allowed. The implementation must validate the connected peer address against the exact allowlist on every connection and make no DNS lookup. The source is never client-selectable.

Redirects are never followed: any `301`, `302`, `303`, `307`, or `308` produces `502` and zero requests to the redirect destination. The transport must not use a redirect-following default. The target operation has a hard timeout of 2 seconds and a bounded response read of 64 KiB. No application retries, library retries, DNS/address failover, connection pooling across authority changes, streaming, callbacks, target-provided URLs, or response-ID follow-up requests are allowed in V1.

The target request uses a fixed safe header set and no client headers. The observation credential is never forwarded to the target. The configured target must be a proven business-state read-only health endpoint: implementation tests must snapshot target state before and after a successful and failed request and assert no business-state, configuration, session, memory, approval, rollback, or write endpoint changed. Ordinary target access logs/metrics are permitted operational side effects; they must not contain credentials or raw request content.

Accepted and rejected requests may produce one bounded sanitized audit record in the observation service journal: timestamp, fixed identity, fixed action, outcome code, and target-contact boolean. No request body, headers, credentials, target body, path, attacker-controlled text, or response identifiers may be logged. Audit retention is bounded by the service journal policy and is not MemPalace or Hermes session storage.

## Service/process boundary

The observation service runs as a separate systemd service and OS identity from normal Hermes. The service account:

- cannot read `API_SERVER_KEY`, generic Hermes credentials, AI Country mutation credentials, MemPalace writer credentials, or unrelated provider credentials;
- has a separate environment/configuration directory and no ambient credential fallback;
- has a restricted filesystem and no write access to Hermes session databases, MemPalace storage, AI Country authority stores, repositories, or system configuration;
- has no inherited mutation-capable file descriptors or generic listener socket;
- has restricted network egress limited to the fixed health target and its own listener dependencies;
- cannot connect to the normal Hermes listener or mutation service;
- runs with no terminal, shell, code-execution, subprocess, delegation, cron, browser-control, device-control, approval, deployment, or credential-management capability.

The observation service has zero MCP servers in V1. It uses a fixed server-owned read adapter for the one health action. No Hermes agent/tool runtime is needed for this fixed action. This avoids accidentally inheriting the current broad MCP inventory, including MemPalace, n8n, Cloudflare, Home Assistant, and agent bridges.

If a future action requires a read-only tool, it must add a separately named, explicitly allowlisted tool/MCP identity and repeat the same boundary review. It must not widen V1 by accepting arbitrary tool fields.

## AI Country client contract

AI Country adds a new narrow `ObservationClient` protocol containing only:

```text
observe_ai_country_health() -> ObservationHealthResult
```

The client does not subclass, wrap, or adapt the current `HermesAdapter`, `SanitizingAdapter`, `RealHermesAdapter`, or `FileCredentialBroker`. It has no methods or fields for generic runs, polling, cancellation, session closure, memory ingestion, memory deletion, retries, approvals, arbitrary providers, models, tools, MCPs, URLs, profiles, or operations.

It holds only the separate observation credential reference and fixed observation endpoint configured by the service deployment. The endpoint is not supplied by an AI Country request. Classification can select whether the fixed observation route is eligible, but classification cannot grant a new action or authority.

A mutation-shaped or prompt-injected request routed to this client can only invoke the fixed health action. It cannot be serialized into a mutation operation.

## Required acceptance proof

The implementation is not clear until all are proven with static, unit, and behavioral integration tests where applicable:

1. Wrong/cross credentials fail before body parsing, action lookup, audit of attacker input, or target contact.
2. Generic credentials cannot authenticate to observation; observation credentials cannot authenticate to generic Hermes.
3. Exact route/method enforcement rejects alternate paths, encoded paths, query/fragment authority, and method overrides.
4. Duplicate keys, extra fields, malformed encodings/content types, unknown actions, nested/array bodies, and oversized payloads fail closed.
5. Observation credentials attempting generic run/chat/session/approval/stop/memory/mutation paths produce zero connections to a mutation-capable trap.
6. The observation process has zero MCP tools in its effective registry and cannot reach the normal Hermes listener, generic credential files, MemPalace writer, or mutation service. The implementation/protocol gate may prove the configured route and tool absence in a hermetic test harness; effective host service identity/filesystem/descriptor/egress proof is a separate pre-activation boundary-verification gate.
7. Fixed target read succeeds; target writes receive zero requests.
8. Redirect targets receive zero requests and zero credentials.
9. SSRF, target substitution, hostile headers, target-provided links, and response identifiers cannot cause follow-up traffic.
10. Revocation and rotation work across restart/reload/concurrency/replay without widening authority.
11. Forced AI Country misclassification of mutation-shaped language still invokes only the fixed read action.
12. No session, memory receipt, memory write/delete, approval, rollback, or normal Hermes run is created.
13. The implementation/protocol gate proves the service-unit template, route table, fixed target, and zero-MCP configuration match this contract. A separate pre-activation gate must inspect the effective running systemd unit, OS identity, filesystem, environment, file descriptors, egress, route table, and MCP configuration before any live canary.
14. The live canary remains a separate owner-controlled gate and is not part of implementation or contract review.
15. Revocation/rotation tests define the concurrency boundary: requests arriving after revocation fail; already-authenticated requests are not allowed to start new target connections after revocation; an in-flight target request may complete only as a bounded read and cannot trigger retries or follow-up work; replayed bodies after rotation/revocation fail.
